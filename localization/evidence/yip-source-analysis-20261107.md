# Recurring kobold vocalization: source investigation

A broad, case-insensitive `yip` substring search over both pinned Yarn text tables and all compiled `RunCommand` operands is implemented in `localization/inventory_yip_cases.py` SHA-256 `cd21ec65416455802b0838874b4cba2e7f628fc032a7200f3eb68a0461dfc734`. The source-bound result `yip-source-context-20261107.json` SHA-256 `9805ba6aa48dce7c7c672f41f589339ac840945be0738c1ac64fb541fce32abc` records 20 matching text IDs in 12 nodes and 13 matching sound commands in each build. The full mapped text context of those nodes contains 231 distinct IDs; three surrounding source values differ across builds, so both source fingerprints are retained. The search includes names such as `Yip-Man` and intentionally admits possible false positives; it is a candidate finder, not proof that other linguistic forms or other resource families are absent. Complete branching, dynamic callers and all source scenes remain under review.

The vocalization occurs as a player response, as a word discussed by characters, and in a branching Alexander scene where one repeated sound has different parenthesized meanings. The title `Yip-Man` is offered in a separate scene and referenced later. The two preliminary cases, their full 231-ID and 45-ID node contexts, exact candidate IDs and pending editorial decisions are recorded in `special-scenes-yip-20261107.json` SHA-256 `fee1920f8fa1faa5e3739d92181a9b221c9865a31e4776155dfca4324786d7e8`. The contexts overlap intentionally. A consistent Russian rendering and film-title treatment have not yet been chosen; all related branch identities, markup and source controls remain exact.

All 13 compiled sound commands in each build are `PlaySFX "yip"`. Static IL inspection of both `Assembly-CSharp.dll` files shows command registration binds `PlaySFX` to `WalkNWashSceneState.PlaySFXByName`, which compares the supplied key against each serialized sound object's name before requesting playback. The extracted IL text for the selected registration and method was byte-identical between builds, SHA-256 `55fbaf6a36d1ef3ec47fac8f8643c9cb91da772f18319f873214ef9449c37b7e` in local work. The command and `yip` lookup key are runtime identities, not translatable dialogue.

`localization/inventory_yip_audio.py` SHA-256 `b0fde3cb89b7063680bd2a2afc861e04e32c283bc739998abc2dd82901506093` verifies the level1 `WalkNWashSceneState` field through a byte-exact schema round trip in each build. Its pinned reports are `yip-audio-macos-20261107.json` SHA-256 `ae5278be5f72801f310fc4ca12fc51d6c378b2a252ae52e6daf43c98d4dac2b5` and `yip-audio-windows-20261107.json` SHA-256 `b01230d46ccac3f1d09c5cb3dae7f2508bd939eb85643fa0a7b74e315da3516d`. In each source, that array refers to an `AudioClip` named `yip` in `sharedassets1.assets`; both serialized clip objects and their 7,648 encoded resource bytes match. This is a source-object and byte-range trace, not decoded audio, a playback test, proof for other scenes or a decision to translate audio.

Reproduce the text report with `inventory_yip_cases.py --macos-data <original macOS Data> --windows-data <original Windows Data>` and each audio report with `inventory_yip_audio.py <macos|windows> <original Data>`, using pinned dependencies. All three reports reproduced byte-for-byte. Three focused tests cover candidate matching, complete node context with different per-build wording and a changed source fingerprint. A copied Windows resource with one altered audio byte was rejected at the intended source-hash guard after the real inputs passed. Neither game installation nor original audio was changed.
