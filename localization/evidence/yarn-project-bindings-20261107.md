# Yarn project bindings and bounded runtime probe

`localization/inventory_yarn_bindings.py` SHA-256 `e5fdb49c5fbde224eba5fd742dad6d5ae44cee53f4e9ad514b6bbcac03d9807e` scans fifteen hash-pinned serialized assets in each installed build, resolving script identities against the pinned global script inventory. Its records are `yarn-bindings-macos-20261107.json` SHA-256 `d7bc0340f364a1b3d376318539fb5c7f0429fa161fd2010a828e878f1435edd7` and `yarn-bindings-windows-20261107.json` SHA-256 `e20584a4b0dfd2cff85a51918b79a6380219cfdbd896c02c494c6488cab0ddf0`. Each scan found no unresolved script references, one `YarnProject` in `sharedassets1.assets`, and one `DialogueRunner` in each of `level1`, `level3`, `level4`, `level5` and `level6`. All five runners in each build serialize a reference to the sole discovered project, with `autoStart` false. Their schemas and complete objects passed no-op byte comparison. The project object hashes match those used by `yarn-targets-20261107.json`. These counts cover only the fifteen named assets and the two named script types, not all possible runtime sources.

Static IL inspection of the two pinned `YarnSpinner.Unity.dll` builds showed `DialogueRunner.StartDialogue` obtains the current `yarnProject.Program`, calls `Yarn.Dialogue.SetProgram`, then calls `SetNode`. It subsequently awaits the dialogue presenters before calling `Yarn.Dialogue.Continue`; an exception in that asynchronous method is passed to the task builder. This supports the serialized binding finding but does not rule out runtime replacement of the project, altered input, dynamically loaded programs or different game code paths.

Four bounded macOS tests used separate copied games, fresh test profiles, synthetic six-line locale inputs and test-only instrumented `Assembly-CSharp.dll`; neither a translated build nor a natural story traversal was tested. Each identified process was terminated and the wrapper removed its temporary Steam file and verified the test copy's signature:

1. `G6PQ` installed a hook at `WaitingToBeLetIn`; the isolated game reached `WalkingToWindow` but did not reach the hook during observation. Log SHA-256 `aaadfb2ac6003b728fdfb7116e9eabb3c0bd548b511c6f88807e4715315ea7c7`.
2. `G6PR` called `DialogCommands.StartDialogue("RyanDate_Outro", true)` at the end of `StartCurrentLevel`. It stopped at the unrelated precondition `Could not find dragon for dialogue`; it did not test the target transfer. Log SHA-256 `39d09b2ea15e07c3cc43e4e62bcc2b17657264df3ec9f6de167ca63294a8f776`.
3. `G6PS` moved the hook to the later `WalkingToWindow` transition; the process lost foreground focus and did not reach that hook during observation. Log SHA-256 `e55f5964b3d71ab93a64a54428e688caaa4376eae890b6d6d5c8c411d66d1d8f`.
4. `G6PT` enabled background operation in its test bridge and invoked the same node after `WalkingToWindow`. Log SHA-256 `40d00116eebf2c583f2d22b65d5c242f7e3662185a3ea785c06dd0b60aeb4b7a` records `Running node RyanDate_Outro` but no missing-target exception or continuation evidence during a further 20-second observation. The source project object and both Yarn runtime DLLs in this test copy were verified byte-identical to the pinned originals. The test bridge DLL SHA-256 was `c8d061bcdfcd301a28b751bbf605eef7398b14a568e40ee1e2641eb204338103`; its task-owned source is `localization/work/missing-target-background-patcher/Program.cs`, SHA-256 `0b79725b39f715c88d2c7ec84d66f00414d3576086402ff19bb42b9d1084d01c`. The localized table had six synthetic substitutions, none asserted to be a release translation.

The final test establishes that the forced entry node was selected. It does not show that the runner passed the presenter wait, executed its first instruction, reached the missing node, or completed/faulted its asynchronous task. Therefore it neither proves nor disproves the predicted missing-target failure. Reachability, async task state and a positive continuation control remain to be investigated. The installed game's original `Assembly-CSharp.dll` hash and the original profile file inventory/hashes matched their earlier baselines after the tests.

Reproduce static binding reports using `inventory_yarn_bindings.py <macos|windows> <original Data directory>` and the project's pinned dependencies; both reports reproduced byte-for-byte. The positive check asserted all ten runner-to-project references and no unresolved script references; changing a copied Windows `level0` byte was rejected at the intended source-hash guard. Runtime probe artifacts are retained in task-owned work, not release files.
