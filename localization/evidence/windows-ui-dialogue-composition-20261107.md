# Windows UI and dialogue composition

At commit `ffa61c3`, `localization/windows_ui_locale.py` SHA-256 `aa59bc41739a6677eb9c0b5c3077893c519e4ead2eb54dcd222709b93266bf5b` optionally accepted `--dialogue-locale-file` when building `sharedassets1.assets`. It starts from the exact original Windows asset, validates the separate UI and Yarn source fingerprints and locale codes, derives both changed objects, serializes a single file, and compares every output object's raw bytes to either its exact source or its expected replacement. The Yarn object is also decoded to verify its complete ordered IDs, values and metadata before serialization. No intermediate modified asset is trusted as input. The existing no-overwrite and individual-file publication boundary described in `windows-ui-adapter-20261107.md` remains in effect. That checkpoint did not compose settings, code patches or other assets into an installation. The subsequent settings extension is documented in `windows-ui-settings-composition-20261107.md`; source classification and release checks remain incomplete.

The focused suite `test_windows_ui_locale.py` SHA-256 `c7b40736ae4e8e530733b1ca0d0cc9bf438fde18919e8bfea2e38f967cce4572` now contains 11 tests. The combined positive control independently compared every output object against the original or its expected UI/Yarn bytes. Negative controls rejected mismatched locale codes, a wrong target asset and a stale dialogue source. An injected read-back failure after temporary serialization published neither change and removed the newly created temporary file. The complete suite passed 74 tests.

The raw object was independently verified in the combined asset, but it was not expected to remain visible once an option is populated: static IL inspection of the pinned Windows `Yarn.Unity.OptionItem.set_Option` shows it obtains the localized option line and assigns that value to the TMP text field.
